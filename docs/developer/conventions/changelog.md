# 更新日志写法

读者是装了 Ophel 的用户：会用浏览器和 AI 对话网站，但不看代码。他们在应用内的更新提示、更新弹窗、GitHub Release 和官网更新日志页里看到这几行字，想知道这次更新跟自己有什么关系。

修改 `CHANGELOG.md` 时，如存在 `CHANGELOG.zh-CN.md`，必须同步更新中英文两份日志。两份含义一致，各按自己语言的习惯写，不要逐字互译。

## 写到什么程度

目标是「看得懂、讲得清」。有三种写偏的情况：

- **太堆砌**：一句话里塞好几个读者认不出的词（节点、挂载、文档流、视口、主线程），或者用代码里的叫法、自己起的名字称呼界面上的东西（流光提示、可见安全区）。判断办法：你自己得翻代码才能解释的词，读者肯定看不懂，换掉。
- **太空**：只有「更清晰、更流畅、体验优化」这类形容词，读完不知道到底变了什么。
- **太随意**：为了通俗，把做了什么全删掉，只剩一句口头禅（「不卡了」「顺滑多了」）。

刚好的写法：用日常软件用语（同步、刷新、加载、滚动、后台检查、重复扫描……）说清改了什么，再落到用户能感觉到的结果。可以带一点技术味，但每个词都得是读者听得懂的。

## 怎么写

动笔前先想清楚三件事：

1. **谁会碰到**：在什么场景下（哪个站点、点了哪个按钮、开了哪个设置）。
2. **以前怎样**：做不到、很麻烦，还是出了什么问题。
3. **现在怎样**：能做什么、少了什么、不再出什么问题。

写的时候：

- 称呼界面上的东西，优先用界面上的文字，照原文写，如「去顶部」「禅模式」。界面上没有文字的元素，用「位置 + 外观或作用」说，如「导出按钮上的闪光提示」；说不清、又不重要，就不写。
- 文件名、函数名、CSS、像素值、接口名留给 commit 和 PR 描述。
- 概括也要有一个看得见的落点：数字（「从 10 项减到 8 项」）、按钮名、站点名，都比形容词有用。

## 写完自检

有一条没过就重写。

- **看得懂测试**：把这条给一个会用 Ophel、没看过代码的人看，他能说出「哪个功能、发生了什么、结果怎样」吗？
- **划掉测试**：把「更清晰、更流畅、更便捷、更统一」这类形容词划掉，句子里还剩什么具体信息？没剩下，回去查清楚变了什么再写。「优化」「提升」后面也必须跟着具体对象和结果，不能只有「优化 XX 体验」。
- **一件事测试**：一条只讲一个主题。一条里并列三件以上互不相关的改动，就概括成一个主题，或只留最主要的，其余留在 PR 描述里。
- **重要性测试**：大多数用户会碰到、会受影响吗？不会就不写：小众站点或冷门功能的改动、小细节、顺带做的整理，以及用户察觉不到的改动（重构、测试、CI、文档、依赖、几像素的间距和对齐）。自己说不出变了什么，先去看 PR 描述和界面，还说不清就不写。

## 分类

只用下面三类标题，不要新增性能、UI、文档、国际化、限制等其它标题，除非用户明确要求。

| 中文 | 英文 | 什么时候用 |
| :--- | :--- | :--- |
| `### 🚀 新增功能` | `### 🚀 New Features` | 以前做不到，现在可以：新站点支持、新设置项、新入口 |
| `### ✨ 功能优化` | `### ✨ Improvements` | 以前就能用，现在用法变了：减少操作步骤、响应变快、位置或默认值调整；性能优化通常归入这里 |
| `### 🐛 问题修复` | `### 🐛 Bug Fixes` | 明确的错误行为、兼容性问题或回归，现在好了 |

## 条目格式

`- **标题** — 说明。 (#PR)`

- **标题**：用户认得的功能名或现象。不要把两个技术词硬拼在一起，也不要用「界面优化」「体验优化」这种放哪都成立的标题。
- **说明**：
  - 修复：`在什么场景下，出了什么问题，现在好了。`
  - 新增：`在什么场景下，现在可以做什么。`
  - 优化：`改了什么，用户感觉到什么变化。`
- 动词要具体：新增、支持、改成、移到、合并、去掉、不再、自动、减少。「优化」可以用，但后面要跟具体对象和结果。
- 英文同样一件事一句话，常用 `Fixed an issue where …`、`… now …`、`… no longer …`。

## 一个 PR 写几条

一个 PR 只写一条，概括成一句话。不按 commit、站点或模块罗列；PR 里不重要的改动不写，留在 PR 描述里。

- **概括**：找出这个 PR 最主要的主题（如「设置菜单精简」「手机与平板适配」），用一句话说清，再带上一两个最能代表它的结果。改动再多，也不逐项列出。
- **概括不是空话**：概括是「一个主题 + 一个看得见的落点」，空话是只剩形容词。「界面更清爽、统一」是空话；「悬浮提示统一为应用内样式，不再显示浏览器默认样式」是概括。
- **什么算重要**：大多数用户会碰到，或者碰到时会明显受影响（功能坏了、做不了、用法明显变了）。其余的都留在 PR 描述里。
- **两条是例外**：一个 PR 里有两处互不相关、又都很重要的改动，才拆成两条，很少用。

分支开发中再加日志前，先看本分支有没有已写的条目，有就改写，不要重复追加。

## 常见情况

- **网站改版**：「适配 XX 新版界面」可以写，但后面要带上具体恢复或新增了什么，别只写「适配」二字。
- **性能**：写在哪个场景、哪个操作变顺了，可以带一句做法（如「减少重复扫描」），不写代码层面的原因（节点、主线程、索引计算）。
- **视觉改版**：概括成一条，落在一个看得见的变化上（哪里、变成什么样），不罗列每处样式调整。落不到具体变化就不写，别写「更清爽、更统一」。
- **移除功能、改默认行为**：影响很多人、或会让用户困惑时才写，并说清受影响的用户现在该怎么做。顺带删掉的冷门功能、小众站点的功能不写。

## 示例

标「改写」的是新写的参考，其余是本仓库真实写过的日志。遇到新的坏写法，往这里加一组示例，不要再加一条禁令。

**1. 同样是长对话卡顿，四种写法**

- ❌ 太堆砌：`**ChatGPT 长对话大纲性能** — 优化长对话下的大纲同步与条目索引计算，消除大纲刷新时对页面深层节点的重复全量扫描，缓解主线程掉帧与操作卡顿。`
- ✅ 刚好：`**长对话插入与清除提示词性能** — 优化长对话页面（如 ChatGPT）上的后台检查逻辑，消除对整页内容的重复扫描，插入、清除提示词不再卡顿数秒，输入操作恢复即时响应。`
- ✅ 刚好（改写）：`**ChatGPT 长对话大纲性能** — 优化长对话下大纲的刷新方式，不再反复扫描整个页面，缓解刷新大纲时的卡顿。`
- ❌ 太随意（改写）：`**长对话提示词不卡了** — ChatGPT 长对话里插入、清除提示词不再卡几秒。`
- 「条目索引计算」「深层节点」「主线程」要读过代码才懂。「后台检查」「重复扫描」是日常软件用语，后面还落到了「卡顿数秒」「即时响应」这样看得见的结果。只剩「不卡了」，就看不出做了什么。

**2. 读者认不出的元素名，加上一条塞了几件事**

- ❌ `**大纲标签页优化** — 层级滑块支持按住拖动调整，窄面板下工具栏自动精简，优化行对齐细节，导出按钮的流光提示点击后不再重复出现。`
- ✅（改写）`**大纲层级滑块与工具栏** — 大纲的层级滑块现在可以按住拖动调整；面板较窄时，大纲工具栏会自动精简。`
- 「流光提示」是自己起的名字，「行对齐细节」用户看不出来，这两处直接不写。

**3. 把页面排版术语搬进来**

- ❌ `**净化模式底部间距保持** — 净化模式在隐藏输入框下方的 AI 生成声明与免责提示时，完整保留站点原有的文档流高度与间距，避免输入框紧贴视口底部，还原原生视觉比例。`
- ✅（改写）`**净化模式底部间距** — 净化模式隐藏输入框下方的 AI 生成声明和免责提示后，输入框不再紧贴窗口底部，会保留站点原有的间距。`
- 「文档流高度」「视口」「原生视觉比例」换成用户看得到的现象：输入框是不是贴底。

**4. 把代码搬进日志**（示意，非原文）

- ❌ `**MainPanel 单 Tab DOM 门控优化** — 在 MainPanel.tsx 中当 visibleTabs.length <= 1 时移除 .gh-panel-tabs 节点渲染，节省 38px 空间。`
- ✅ `**单标签页自动隐藏** — 仅开启一个功能时自动隐藏顶部切换栏，释放纵向空间展示更多内容。`
- ❌ `**快捷工具栏 z-index 与 pointer-events 调整** — 修复浮动面板 CSS 层级覆盖导致的 click 事件穿透捕获失效。`
- ✅ `**工具箱菜单被面板遮挡** — 修复吸附模式下点击快捷工具栏时菜单被面板盖住的问题，现在菜单始终位于面板之上。`

**5. 只剩形容词**

- ❌ `**界面 UI 优化** — 面板、设置页和各类弹窗的界面更清爽、统一。`
- ✅ `**统一悬浮提示样式** — 面板、设置页和各类弹窗里的悬浮提示统一为应用内样式，不再显示浏览器默认样式。`
- 两条来自同一个 PR，写一条就够。划掉「更清爽、统一」后什么也不剩，改措辞救不了，只能回 PR 描述找一个看得见的变化。PR 里的其余改动（备份导入、主题配色……）不逐条写。

**6. 好的例子：一个 PR 一句话**

- ✅ `**站点设置交互优化** — 在站点设置页顶部选好站点，这个站点的所有设置都在同一页里，不用再来回切换。`
- ✅ `**设置菜单精简** — 设置菜单从 10 项减到 8 项：全局搜索设置移到「功能模块」，权限管理移到「数据与权限」。`
- ✅ `**Gemini 新版界面适配** — 适配 Gemini 统一后的新版界面，任务（原 Spark）对话现可正常同步至对话管理，并修复新对话页输入框自动隐藏失效的问题。`
- 前两条对应的 PR 都改了很多处（旧链接的跳转、搜索入口的更新、顺带删掉的冷门设置……），日志里只写用户一眼能懂的那个主题。「适配」可以用，关键是后面跟着具体恢复了什么；「从 10 项减到 8 项」这样的数字比形容词有用。

**7. 英文同理**

- ❌ `Optimized heading sync and index calculation during long conversations, eliminating repeated full-tree DOM queries and reducing main thread lag during outline refreshes.`
- ✅（改写）`Optimized how the outline refreshes in long conversations: the page is no longer scanned repeatedly, easing lag during refreshes.`

## 位置、编号和发版

- 新条目追加到 `[Unreleased]` 对应分类列表的**末尾**，不要插在首行，以免打乱已有条目的顺序。
- 来自 PR、issue 或外部贡献者时，能确认就在条目末尾保留编号和贡献者，不要遗漏，也不要凭空补。格式：`(#645)`、`(#547, @urzeye)`、`(#593, #625)`。中英文两份保持一致。
- 发版后，版本里的**第一条**会显示在应用内的更新提示里（`src/components/App.tsx` 的 `releaseNotesPreview`，去掉加粗和末尾编号后原样显示）。发版前确认第一条是最想让用户看到的，而且单独读也读得懂。
