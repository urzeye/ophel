# 交互做减法与用户引导现状分析

> 基于 `suggestion.md` 的反馈，对「1. 交互做减法」「2. 用户引导 + 动线」两个方向的代码现状盘点。
> 边界：Ophel 是对话增强插件，不引入 AI / skill / MCP。本文只做分析，不含代码改动。
> 分析日期：2026-11-19。

## 一、交互做减法：设置面现状

### 1.1 设置项规模（代码实测）

| 位置 | 规模 |
| --- | --- |
| `FeaturesPage.tsx` | 1,861 行，约 94 个 `SettingRow`，分 16 个 `SettingCard` 分组 |
| `GeneralPage.tsx` | 900 行，19 个 `SettingRow`，5 个分组 |
| `ShortcutsPage.tsx` | 约 46 个可配置快捷键动作（`SHORTCUT_ACTIONS`） |
| 快捷按钮 | 10 个按钮各有独立开关 + 排序（`DEFAULT_COLLAPSED_BUTTONS`） |
| 布局矩阵 | 6 个功能（pageWidth / userQueryWidth / zenMode / cleanMode / panelAvoidance / autoHideInput）× 最多 16 个站点分别可配（`DEFAULT_SETTINGS.layout`） |
| 主题矩阵 | 8 个站点各自独立主题配置（`theme.sites`） |
| 站点专属设置页 | ChatGPT / Gemini / Claude / AI Studio 各有独立设置页 |
| 文案规模 | `zh-CN/index.ts` 1,923 行（×11 种语言同步维护） |

`FeaturesPage` 的 16 个分组为：通知、用量监控、标签页行为、隐私模式、大纲、书签、滚动、导出、对话、提示词、快捷引用、阅读历史、交互增强、全局搜索匹配、全局搜索提示词、模型锁定。

### 1.2 结构性问题

1. **没有分层机制，一律平铺。** `SettingCard` / `SettingRow` 没有折叠、高级区、二级页等分层能力，所有频率的设置在视觉上等权。94 行平铺意味着用户进入功能页先面对一堵开关墙。
2. **开关与行为耦合的历史包袱。** 一批设置项默认值就等同于"正确行为"，开关存在的主要意义是兼容极少数反对者，例如 `folderRainbow`（文件夹彩虹色）、`syncDelete`、`hideStatusWhenRead` 这类。这与建议中"收起/展开类需求溢出开关"的批评一致。
3. **矩阵型配置放大认知成本。** 布局 6×16、主题 8 站点的 per-site 配置对单站点用户几乎全是噪音，但占据了 `DEFAULT_SETTINGS` 的绝大部分体积，也放大了备份/迁移/i18n 的维护面。
4. **快捷键 46 个动作全量平铺。** 其中 expandLevel1~6、switchTab1~3 等是同族动作，适合收敛为分组呈现。

### 1.3 已有的缓解因素

- 全局搜索已覆盖设置项检索（`src/components/global-search/settingsSearch.ts`），会用搜索的用户可以绕过平铺。
- 部分分组（通知、隐私模式）内部已有条件显隐（子项仅在父开关开启时出现）。

### 1.4 减法候选方向（分析建议，非裁决）

- **分层优先于删除**：给 `SettingCard` 增加折叠/高级区能力，把 94 行压成"首屏 20 行 + 其余收进高级区"，收益最大且不破坏任何现有用户配置。
- **同族收敛**：expandLevel1~6、switchTab1~3、通知重复次数/间隔等成组项，合并为单控件或预设档位。
- **删除候选的特征**：默认值即正确行为、改动后无人受益、且可通过 persist 数据迁移静默移除的开关。逐一枚举前建议先加一层"设置项改动埋点"或在社区发一次投票，避免误删真实有人在用的项。
- **新增纪律**：新功能默认不加配套开关，行为做对优先，可配置是兜底手段。

## 二、用户引导：已有机制与缺口

### 2.1 已有引导机制清单

| 机制 | 位置 | 持久化 | 触发与退出 |
| --- | --- | --- | --- |
| 首次免责/欢迎弹窗 | `DisclaimerModal.tsx` | settings store（`hasAgreedToTerms`） | 首次启动强制展示，同意后永不出现 |
| 版本更新日志 | `ReleaseNotesModal.tsx` | release-notes 已读标记 | 检测到未读版本时弹出 |
| 导出按钮流光 | `useExportDiscovered.ts` + `OutlineTab.tsx` | platform.storage（`ophel:exportDiscovered`） | 未点击过导出按钮时持续流光，首次点击后永久停用 |
| 全局搜索快捷键 nudge | `useGlobalSearchShortcutNudge.ts` | localStorage | 有最大展示次数、最小间隔、快捷键用够次数自动停、可"不再提示" |
| 对话空态 + 同步提示 | `ConversationsTab.tsx` | store（`markSyncHintSeen`） | 空列表时展示"新对话会存入所选文件夹"等文案 |
| 大纲空态 | `OutlineTab.tsx` | 无（状态即文案） | 无大纲内容时展示说明文案 |
| SitePack 绑定引导 | `SitePacksPage.tsx` | — | 自部署包未绑定时引导切 tab、预选、高亮表单 |
| Safari 授权指引 | `SafariWebsiteAccessGuide.tsx` | — | Safari 平台定向指引 |

### 2.2 评价

已有的引导是**单点式、发现式的**：针对单个功能（导出、全局搜索），做得克制且成熟（有频控、有退出、用会即停），这套模式可以直接复用。

但存在两个结构性缺口：

1. **引导状态各自为政。** 三种持久化并存（settings store / platform.storage / localStorage），没有统一的"引导注册表"。每加一个引导都要重新发明状态结构、频控和退出逻辑，油猴端还要注意 localStorage 是按站点隔离的。
2. **没有首次安装引导。** `chrome.runtime.onInstalled` 只做网络规则、远程配置、SitePack 注册的调度（`background.ts:316`），不打开任何欢迎页或导览；`DisclaimerModal` 是唯一的首启触点，但内容纯合规（免责+隐私），用户同意后被直接扔进完整面板，没有任何"这三个 tab 分别是什么"的指引。

### 2.3 首装引导的设计约束（从代码结构推导）

- 首启触点已有挂载点：`DisclaimerModal` 同意后是天然的引导起点，不需要新增安装钩子，也不应再叠一个全屏蒙层打断。
- 引导应复用现有单点模式：低打扰、可"不再提示"、用会即停、状态集中管理。
- 双平台约束：引导状态若要跨站点一致，须走 platform.storage，不能走 localStorage（油猴端按站点隔离）。
- 成本约束：任何新增引导文案都要同步 11 种语言 ×（应用内 + manifest）两套体系，引导步骤越多文案成本越高，首版应控制在 3 步以内。

## 三、动线：现状与缺口

### 3.1 已存在的动线基础

1. **新对话入库已有默认归处。** 同步入库时 `folderId` 缺省即落 `inbox`（`src/core/conversation/manager.ts` 的 `getValidFolderId`，空值和失效值都归一到收件箱）；收件箱是固定首位、不可删除的默认文件夹（`DEFAULT_FOLDERS`，`folders-store.ts`）。
2. **"存入所选文件夹"已经半存在。** `lastUsedFolderId` 持久化记忆用户上次选择的文件夹，新同步对话会进入该文件夹（`manager.ts:783`、`ConversationsTab.tsx:521`），空态文案也在提示这一点。但这个机制是隐式的：用户不打开对话 tab 就不会感知到"当前归到哪个文件夹"。
3. **批量整理能力已具备。** 对话 tab 有批量模式、Shift 范围连选、批量移动/置顶（`ConversationsTab.tsx:449,631`），手动分诊的工具链是齐的。

### 3.2 缺口动线

对照建议中"新创建对话后弹出窗口选择文件夹归类"的设想，现状缺口不是能力而是**触发时机与可见性**：

1. **新对话归类提示（缺口）。** 入库即静默落 inbox/上次文件夹，没有任何时机让用户做归类决策。可行形态：新对话首次入库后，在对话 tab 或面板给一条轻提示（非弹窗）："新对话《标题》已存入收件箱 · 移动到…"，复用 `lastUsedFolderId` 让默认选项就是上次文件夹，一次点击完成；配"不再提示"退出。注意建议原文说的是"弹窗"，但结合"减少交互重量"的总基调，轻提示条比弹窗更一致。
2. **收件箱分诊入口（缺口）。** 批量能力存在但没有场景化入口：用户面对 300 条收件箱时，需要自己发现批量模式。可行形态：收件箱对话数超过阈值（如 20 条）时，在收件箱顶部出现"开始整理"入口，点击直接进入批量模式。
3. **功能发现动线（部分缺口）。** 导出、全局搜索已有发现式引导；大纲书签、阅读历史、提示词变量等中等深度功能没有任何引导，依赖用户自己翻设置。

## 四、结论：优先级建议

1. **设置分层（做减法的主力）**：给 `SettingCard` 加折叠/高级区，先把 `FeaturesPage` 的 94 行平铺压出层次；删除具体开关放到分层之后、有数据或投票支撑再做。
2. **首装引导（空白补齐）**：以 `DisclaimerModal` 同意后为零号触点，做 ≤3 步的面板导览（大纲/对话/提示词三个 tab 是什么）；引导状态收敛为统一注册表 + platform.storage。
3. **两条短动线**：新对话归类轻提示（复用 `lastUsedFolderId`）；收件箱超阈值出现"开始整理"入口（复用现有批量模式）。两者都走已有"单点引导"模式：可退出、用会即停。
4. **不做**：弹窗式强制归类、引导式全屏 tour、为引导新增设置开关。
