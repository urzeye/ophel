# 更新日志写法

读者是装了 Ophel、不看代码的用户，会在应用内更新提示、更新弹窗、GitHub Release 和官网看到这几行字。改 `CHANGELOG.md` 时同步改 `CHANGELOG.zh-CN.md`：含义一致，各按自己语言的习惯写，不逐字互译。

## 核心规则

1. **一条一句话**：说清「改了什么 + 用户看到的结果」就停。说明部分中文不超过 70 字，英文不超过 40 词。
2. **不写细节和举例**：括号举例（如 Claude 的 artifact 页面）、触发条件、实现方式、顺带的小改动，都留给 PR 描述。
3. **按主题合并**：同一主题的多个 PR（如都是设置页整理）合成一条，编号并列，如 `(#987, #988)`。一个 PR 的次要改动并进主条目，不单独成条。
4. **只写多数用户会碰到的**：小众站点、冷门功能、用户察觉不到的改动（重构、文档、CI、依赖、几像素的间距），以及 PR 描述里写明不进日志的，都不写。
5. **说人话**：界面元素用界面上的原文（如「去顶部」），其余用日常软件用语（同步、刷新、滚动）；不写文件名、函数名、CSS、像素值，不自己起名字称呼界面元素。

## 写完自检

- 给一个会用 Ophel、没看过代码的人看，他能说出「哪个功能、结果怎样」吗？
- 划掉「更清晰、更流畅、更统一」这类形容词，还剩具体信息吗？「优化」后面必须跟对象和结果。
- 有括号举例，或超过一句话吗？有就删到只剩主干。

## 分类与格式

只用下面三类标题，不新增其他分类。

| 中文              | 英文                  | 用在                                         |
| :---------------- | :-------------------- | :------------------------------------------- |
| `### 🚀 新增功能` | `### 🚀 New Features` | 以前做不到，现在可以                         |
| `### ✨ 功能优化` | `### ✨ Improvements` | 以前就能用，现在用法变了（性能优化也归这里） |
| `### 🐛 问题修复` | `### 🐛 Bug Fixes`    | 明确的错误行为、兼容性问题或回归，现在好了   |

条目格式：`- **标题** — 说明。 (#编号)`

- 标题用用户认得的功能名或现象，不用「界面优化」这种放哪都成立的词。
- 修复写「在什么场景下，出了什么问题，现在好了」；新增写「现在可以做什么」；优化写「改了什么，用户感觉到什么」。动词要具体：新增、支持、改成、移到、合并、去掉、不再、自动、减少。
- 「适配 XX 新版界面」后面要跟具体恢复了什么，别只写「适配」二字。
- 英文常用 `Fixed an issue where …`、`… now …`、`… no longer …`。

## 编号、位置和发版

- 编号先用 `gh` 核实再写，issue 和 PR 容易混：写 PR 号，有对应 issue 时写 `(#issue, #PR)`，外部贡献者加 `@用户名`；确认不了就不写，不凭空补。中英文两份保持一致。
- 整理整版日志：用 `gh pr list --state merged` 拉出上次发版以来的 PR，读完描述再按主题分组写。
- 新条目追加到 `[Unreleased]` 对应分类的**末尾**；本分支已有同主题条目就改写，不重复追加。
- 版本里的**第一条**会显示在应用内更新提示里（`src/components/App.tsx` 的 `releaseNotesPreview`，去掉加粗和末尾编号后原样显示，反引号不会渲染）。第一条要是最想让用户看到的，单独读得懂，且不含反引号。
- 移除功能或改默认行为：影响很多人才写，并说清用户该怎么办；冷门功能的移除不写。

**只剩形容词**

- ❌ `**界面 UI 优化** — 面板、设置页和各类弹窗的界面更清爽、统一。`
- ✅ `**统一悬浮提示样式** — 面板、设置页和各类弹窗里的悬浮提示统一为应用内样式，不再显示浏览器默认样式。`
